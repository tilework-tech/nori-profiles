# Noridoc: registry-download

Path: @/src/cli/commands/registry-download

### Overview

The registry-download command downloads and installs skillset packages from the Nori registry. It handles version resolution, tarball extraction, skill and subagent dependency downloading, and skillset activation. This is the primary way users obtain skillsets from public or private registries.

### How it fits into the larger codebase

Registered via `@/src/cli/commands/noriSkillsetsCommands.ts` as the `download` command. It calls `@/cli/commands/init/init.js` to auto-initialize if no config exists. It searches registries using `@/api/registrar.js` (including `getSubagentPackument` and `downloadSubagentTarball` for subagent deps), resolves auth tokens via `@/api/registryAuth.js`, and manages skillset metadata through `@/norijson/nori.js`. Skill and subagent dependencies declared in a skillset's `nori.json` are downloaded inline via `downloadSkillDependencies` and `downloadSubagentDependencies`. The interactive search/download flow is driven by `@/cli/prompts/flows/` callbacks. All package mechanics — per-registry search, extraction, atomic replacement, and `.nori-version` provenance — come from the shared primitives in @/src/packaging/ (see @/src/packaging/docs.md).

This command is the enforcement point for the **manifest/receipt split** described in @/src/norijson/docs.md: it is the only place that installs a skillset's whole dependency set, so it is also where the installed `nori.json` is normalized to unpinned dependency specifiers via `unpinDependencyVersions`.

### Core Implementation

`registryDownloadMain` loads config **before** parsing the spec so a bare (non-namespaced) name can resolve against the configured `defaultOrg` via `parseNamespacedPackage` (from @/src/utils/url.ts); the `defaultOrg` is passed only when no explicit `--registry` was given, and when a bare name is thereby routed to a non-public org the command logs `formatDefaultOrgNotice` so the redirect is visible. It then follows a callback-driven flow pattern using `registryDownloadFlow`. The `onSearch` callback resolves which registry to use (explicit `--registry`, namespaced `org/package`, or public fallback), fetches the packument, compares versions against any locally installed copy, and returns a status (`ready`, `already-current`, `list-versions`, or `error`). The `onDownload` callback fetches the tarball, installs it via the atomic-replacement primitives from @/src/packaging/atomicReplace.ts, writes provenance via `writeVersionInfo` from @/src/packaging/provenance.ts, and resolves both skill and subagent dependencies from the skillset's `nori.json`. The install target is chosen via `namespacedOnDiskName` from @/src/utils/url.ts, so public packages are written to the `public/` storage bucket (`profiles/public/<name>`) and org packages to `profiles/<orgId>/<name>` (see the storage-bucket model in @/src/norijson/docs.md).

**`syncDependencies`** is the single dependency-resolution seam shared by every path that ends with an installed skillset on disk (both `already-current` branches in `onSearch` and the post-extraction block in `onDownload`). It reads the installed manifest, runs `downloadSkillDependencies` and `downloadSubagentDependencies` in silent mode, then calls `unpinDependencyVersions` from @/src/norijson/nori.ts, returning the concatenated warnings. It returns an empty warning list when the target has no readable `nori.json`. This replaced three duplicated inline blocks that each re-derived the `skills/` and `subagents/` paths and hand-concatenated warnings.

Registry search supports three strategies: explicit registry URL, namespace-derived registry, and public registry. For namespaced packages under unified auth, the org registry URL, membership check, and token acquisition come from `resolveOrgRegistryAuth` in @/src/core/registryAuthResolution.ts; the all-org parallel search and anonymous public paths still build URLs directly via `buildOrganizationRegistryUrl`. The explicit-`registryUrl` branch (used by switch's provenance-pinned re-download) resolves its auth token the same way: it **prefers unified org auth via `resolveOrgRegistryAuth`** when the pinned URL is an org registry the user belongs to (org id extracted via `extractOrgId` from @/src/utils/url.ts, membership taken from `config.auth.organizations`), and only falls back to `getRegistryAuth` for the home org and local dev. This makes the pinned-registry path authenticate identically to the derived-registry path — both the packument search and the tarball download — so a multi-org member whose home org differs from the pinned org still authenticates. When no namespace or registry is specified and the user is authenticated, it searches all configured organization registries in parallel before falling back to public. Per-registry lookup and the version-list / multiple-matches messages use `searchSpecificRegistry`, `formatVersionList`, and `formatMultipleMatchesError` from @/src/packaging/registryLookup.ts, with `registrarApi` fetches and auth-token resolution injected as callbacks. A bare name routed through `defaultOrg` becomes org-namespaced, so it resolves to that single org registry with no public fallback on a miss (dependency-confusion safety). Namespace packages that require auth but the user lacks access produce specific error messages.

### Things to Know

Installs and updates are atomic. Skillset updates go through `replaceDirContentsWithArchive` (preserving locally-managed `skills/`, `subagents/`, and `.nori-version` from the existing directory), fresh installs through `extractArchiveToNewDir` (which removes the partial directory on failure), and skill/subagent dependency updates through `atomicReplaceDirWithArchive` — all from @/src/packaging/atomicReplace.ts, which restores the original directory if anything fails mid-swap. Both dependency downloaders check `.nori-version` (via `readVersionInfo`) for version comparison and skip re-download when already at latest version. The `--list-versions` flag short-circuits the flow to display available versions without downloading. Auto-init is triggered when no config exists, passing `skipWarning: true` to suppress the interactive warning. The `nonInteractive` and `silent` params are threaded from the CLI registration layer through `registryDownloadMain` to both the `initMain` call (which previously hardcoded `nonInteractive: false`) and to `registryDownloadFlow` where they control whether interactive prompts (e.g., "Re-download from registry?") are skipped. The coercion `nonInteractive ?? silent ?? false` is applied at these boundaries so that `--silent` implies non-interactive behavior.

Subagent dependencies are downloaded by `downloadSubagentDependencies`, which reads the *keys* of `noriJson.dependencies.subagents` and downloads each via `registrarApi.getSubagentPackument` and `registrarApi.downloadSubagentTarball`. Both downloaders ignore the declared version value entirely and install `dist-tags.latest`; the version installed is recorded only in the dependency's `.nori-version` file. All install paths (fresh download, update download, and "already-current" re-download) go through `syncDependencies` and therefore run both downloaders. During profile updates, the `onDownload` callback preserves existing `skills/` and `subagents/` directories -- extracted files in those directories from the tarball are discarded so that dependency-managed content is not overwritten by stale tarball content.

**Ordering invariant**: `replaceDirContentsWithArchive` preserves only `.nori-version`, `skills/`, and `subagents/`, so the skillset's own `nori.json` is replaced wholesale from the tarball. `syncDependencies` must therefore run *after* extraction on the re-download path -- run it before and the tarball's (publisher-written, exact) dependency versions overwrite the normalization. Anything that reorders install steps here needs to keep normalization last.

**Both `already-current` branches live in `onSearch`, not `onDownload`.** They run while deciding whether to offer the "Re-download from registry? This will update all skill dependencies." prompt, so dependencies are refreshed and the manifest normalized even when the user then *declines* the prompt. This was the original bug's blast radius: the prompt would upgrade skills on disk while leaving the versions in `nori.json` pointing at whatever the first install resolved.
